# GitHub Pages Content Viewer — Project Overview

This repo (`Jwalker107/BigFix.We`, published at `https://jwalker107.github.io/BigFix.We/`) serves a static, client-side-only content browser for BigFix content stored as `Sites/<SiteName>/Fixlets/**/*.bes` (Fixlets/Tasks/Analyses/Baselines) and top-level `Signatures/*.xml` (BigFix Inventory Signatures). GitHub Pages publishes the whole repo root, so the viewer (`index.html` + `docs/app.js` + `docs/style.css`) fetches `Sites/` and `Signatures/` files directly, same-origin, with no GitHub API calls and no authentication involved anywhere. A generated manifest, `docs/index.json`, drives the sidebar file list and search; it is rebuilt by `scripts/generate_index.py`, which runs automatically after every merge to `main` via `.github/workflows/update-index.yml`.

## Repository Structure

- `index.html` — the Pages entry point. Loads `highlight.js` 11.11.1 from cdnjs (for syntax highlighting), the vendored `docs/vendor/hljs-bigfix-relevance.js` grammar, `docs/app.js`, and `docs/style.css`. Contains the header (brand + "View on GitHub" link placeholder `#repo-link`), the sidebar (`#search-box`, `#tree-root`, status line with Collapse/Refresh buttons, hide/show toggle), and the `#main` content pane with an initial placeholder.
- `docs/app.js` (957 lines) — all viewer logic: repo/branch auto-detection, `docs/index.json` fetch, sidebar tree build/render/filter, per-file fetch + XML parse, per-doc-type rendering (Task/Fixlet/Analysis/Baseline/Signature/unknown), frontmatter-comment ("attribution") extraction, and the description-HTML sanitizer.
- `docs/style.css` (636 lines) — all viewer styling (navy/blue theme, sidebar tree, badges, code/relevance panels, signature detection cards, responsive collapse under 800px).
- `docs/vendor/hljs-bigfix-relevance.js` and `docs/vendor/LICENSE-hljs-bigfix-relevance.txt` — a vendored, Apache-2.0-licensed highlight.js language grammar for BigFix Relevance, pulled from `github.com/bigfix/hljs-bigfix-relevance` v1.0.1. Only the module wrapper was changed (from a CommonJS `module.exports` to a plain `hljs.registerLanguage` call) so it can load via a plain `<script>` tag after highlight.js's browser build, without a bundler. The grammar itself (keyword list, comment/number/string modes) is unmodified from upstream.
- `docs/index.json` — the generated manifest (`{"files": [...]}`), one entry per `.bes`/Signature `.xml` file. Regenerated by CI; not meant to be hand-edited.
- `scripts/generate_index.py` (183 lines) — walks `Sites/**/*.bes` and `Signatures/*.xml`, parses each file's frontmatter comment and XML body, and writes `docs/index.json`.
- `.github/workflows/update-index.yml` — runs `generate_index.py` (and content-ID assignment) on every push to `main` that touches `Sites/**` or `Signatures/**`.
- `scripts/signature-schema.md` — authoritative description of the Signature XML frontmatter fields and `SoftwareIdentityCatalog` body format; cross-checked against `app.js`/`generate_index.py` below.

## Index Generation (`scripts/generate_index.py`)

Run from the repo root as `python scripts/generate_index.py`. Steps:

1. **Enumerate sources.** `find_source_bes_files()` walks `Sites/**/*.bes` (`SOURCE_ROOT = REPO_ROOT / "Sites"`, via `rglob`, so any depth beneath `Sites/<SiteName>/...` is picked up, not just `Fixlets/`). `find_source_signature_files()` walks `Signatures/**/*.xml` (`SIGNATURE_ROOT = REPO_ROOT / "Signatures"`, `rglob` again — in practice these are direct children per repo convention, but the script itself does not enforce "direct children only"). Both yield paths relative to the repo root, sorted.
2. **Parse frontmatter.** `parse_frontmatter(abs_path)` regex-matches the first XML comment in the file (`FRONTMATTER_RE = r"<!--(.*?)-->"`, `re.DOTALL`) and, within it, lines matching `FRONTMATTER_FIELD_RE = r"^([A-Za-z_][A-Za-z0-9_]*)\s*:\s*(.*)$"`. A value wrapped in double quotes has the quotes stripped. First occurrence of a key wins (`fields.setdefault`).
3. **Build a base entry.** `base_entry(source_rel_path)` returns a dict with `path` (posix, repo-root-relative — this is *also* the browser fetch URL and, combined with `BLOB_BASE` in `app.js`, the "View on GitHub" URL), `name`, `dir` (parent dir as posix, or the literal string `"(root)"` if the file has no parent beneath the walked root), `type` (default `"Other"`), `title` (defaults to the filename stem), and empty/zero placeholders for `source`, `sourceReleaseDate`, `severity`, `domain`, `downloadSize`, `relevanceCount`, `author`, `id`, `publisher`, `productName`, `release`, `keywords`.
4. **`describe(source_rel_path)`** — for `.bes` files. Parses frontmatter for `author` (`Author`) and `id` (`ID`). Parses the file as XML; finds the first child of the document root whose tag is one of `KNOWN_ROOT_TAGS = {"Task", "Fixlet", "Analysis", "Baseline", "TaskCondition", "ComputerGroup"}`. If none is found (unparsable or unrecognized), returns the base entry as-is (type stays `"Other"`). Otherwise sets `type` to that tag, and pulls `title` (falls back to filename stem), `source`, `sourceReleaseDate` (from `<SourceReleaseDate>`), `severity` (from `<SourceSeverity>` — despite the JSON key being `severity`), `domain`, `downloadSize`, and `relevanceCount` (a *count* of `<Relevance>` children, not their text).
5. **`describe_signature(source_rel_path)`** — for `Signatures/*.xml`. Always sets `type = "Signature"` (no XML-body inspection or root-tag check at all — Signature classification is driven entirely by which top-level directory the file came from, not its content). Reads only the frontmatter: `author` (`Author`), `publisher` (`Publisher`), `productName` (`ProductName`), `release` (`Release`), `keywords` (`Keywords`). `title` becomes `productName` if present, else the filename stem.
6. **Assemble and write.** `main()` calls `describe` over every `.bes` path and `describe_signature` over every Signature path, concatenates both lists into `entries`, wraps them as `{"files": entries}`, and writes `docs/index.json` with `indent=2`, `ensure_ascii=False`, and a trailing newline. Prints an entry count to stdout.

Frontmatter format (shared by both `.bes` exports and `Signatures/*.xml`, per the module docstring and confirmed live in `docs/index.json`):
```
<!--
  ID       : 2994532
  Author   : jgstew
-->
```
or, for Signatures (values optionally double-quoted):
```
<!--
Author: "edmontan"
Publisher: "3M Company"
-->
```
Cross-check against `scripts/signature-schema.md`: its example frontmatter block (`Description`, `Author`, `uploadedOn`, `Publisher`, `ProductName`, `Release`, `Keywords`) matches the field names `describe_signature` actually reads (`Author`, `Publisher`, `ProductName`, `Release`, `Keywords`) — `generate_index.py` just doesn't surface `Description` or `uploadedOn` into `index.json` (those two are picked up client-side instead, directly from the file's own frontmatter comment, by `app.js`'s `extractAttribution`/`parseFrontmatterFields` — see below). The schema doc's `SoftwareIdentityCatalog`/`Software`/`Signature`/`AND`/`OR`/`PackageFilter` shapes match what `app.js`'s `renderSoftwareList`/`renderSignatureFilterNode` actually walk (confirmed below).

## Viewer App (`docs/app.js`, loaded by the root `index.html`)

### Repo/branch config and the "View on GitHub" link

```js
const DEFAULT_OWNER = "Jwalker107";
const DEFAULT_REPO = "BigFix.We";
const DEFAULT_BRANCH = "refs/heads/main";
const GITHUB_SITE = "github.com";
```
`detectRepoConfig()` inspects `location.hostname`/`location.pathname`: if the hostname matches `^([^.]+)\.github\.io$` and the path has at least one segment, it uses that hostname's owner and the path's first segment as the repo (so a fork served at `https://<user>.github.io/<fork-name>/` links "View on GitHub" back to the fork, not upstream); otherwise it falls back to the `DEFAULT_*` constants above. `DEFAULT_BRANCH` is *not* re-detected from anything — it's always `"refs/heads/main"` regardless of which repo/fork is served. `BLOB_BASE` is `https://github.com/<owner>/<repo>/blob/<branch>/`, used to build both the header's repo link and each doc's "View on GitHub" link. Note `DEFAULT_BRANCH`'s value (`"refs/heads/main"`) is a full ref name, not a bare branch name like `"main"` — it's used as-is in the blob URL path.

### Local content fetch

`INDEX_URL = "docs/index.json"`. `localContentUrl(path)` percent-encodes each path segment and rejoins with `/` — since GitHub Pages serves the whole repo root, an entry's `path` (e.g. `Sites/BigFix Management/Fixlets/Analyses/1-BigFix Client - Evaluation Cycle.bes`) resolves directly to the real file, same origin. No file content is copied or duplicated anywhere; the same `path` value both fetches the file locally and (via `BLOB_BASE`) builds the GitHub blob link and the native `download` attribute link.

### File list / sidebar tree

`loadFileList(forceRefresh)` fetches `docs/index.json` (bypassing cache with `{cache: "no-store"}` only on manual refresh), sorts all entries by `path`, and calls `renderTree`.

Tree building (`buildTree`) groups by each entry's `dir` field verbatim — this is the part that differs from a flat `content/<Type>/` layout: **there is no single common leading segment every entry shares.** `Sites/<SiteName>/Fixlets/...` and `Signatures` are both legitimate, independent top-level branches, so `buildTree` does not strip or special-case any prefix — it splits the full `dir` string on `/` and walks/creates one tree node per path segment (e.g. `Sites` → `BigFix Management` → `Fixlets` → `Analyses` all become nested groups; `Signatures` becomes its own top-level, single-segment group). A file with `dir === "(root)"` (i.e. sitting directly at the repo root with no parent, which in practice does not happen for either `Sites/` or `Signatures/` content) attaches to the tree root with no group wrapper at all. Each directory node tracks its own `files` and a `children` map; `countFilesRecursive` recursively sums file counts for the group-label badge (e.g. `Fixlets (42)`).

Rendering (`renderTreeLevel`/`renderDirGroup`) lists subdirectory groups (alphabetical) before that directory's own files (alphabetical by name), one level at a time; the whole subtree is built up front and folding is pure CSS (`.tree-group.collapsed .tree-files { display: none; }`), so expanding a deeply-nested group never triggers a re-render. Every group starts collapsed by default; while the search box has text, every level starts expanded instead so matches aren't hidden behind a chevron. `renderFileRow` strips a trailing `.bes` extension from the displayed label (Signature `.xml` files keep their extension since the regex only matches `.bes$`), sets a colored `type-dot` per `typeDotClass` (`Fixlet`/`Task` share a blue dot, `Analysis` purple, `Baseline` orange, `Signature` teal, anything else grey), and sets a hover `title` tooltip of `"<title> (<type>)"` when the parsed title differs from the filename.

### File selection, fetch, and parse

Clicking a row calls `selectFile(path)`, which pushes `?file=<path>` into browser history (`history.pushState`) and calls `loadAndRenderFile`. A `popstate` listener re-renders on back/forward navigation. `loadAndRenderFile` fetches the raw file via `localContentUrl(path)`, parses it with `new DOMParser().parseFromString(xmlText, "application/xml")`, checks for a `parsererror` element, and dispatches to `renderDocument`.

### File rendering (`renderDocument` and type-specific renderers)

`renderDocument` branches first on `bes.tagName === "SoftwareIdentityCatalog"` → `renderSignatureDocument` (see below). Otherwise it looks for a direct child matching `:scope > Task, :scope > Fixlet, :scope > Analysis, :scope > Baseline, :scope > TaskCondition, :scope > ComputerGroup`; if none matches, `renderUnknown` shows an error box plus a raw-XML `<details>` (open by default), but still shows the attribution block if one is found. For a recognized root, it renders:
- A title row (`<h1>` from `<Title>`, or the filename if absent) with badges: doc type, severity (`SourceSeverity`, colored by `severity-<lowercased-value>` — CSS defines `severity-critical`/`severity-important`/`severity-moderate`/`severity-low`), and domain.
- A meta line: `Source`, `Released` (`SourceReleaseDate`), `Download size` (`DownloadSize`, formatted via `formatBytes` — bytes/KB/MB), plus the shared `metaLineFooter` ("View on GitHub" link + a same-origin native `download` link, looked up from `allFiles` by matching `path`).
- The attribution section (frontmatter comment, verbatim) if one was found.
- Description, sanitized and rendered as real HTML (see sanitizer below).
- Relevance list (`:scope > Relevance` children), each item syntax-highlighted with the `bigfix-relevance` hljs grammar.
- Type-specific body: `renderActions` for Task/Fixlet (tabbed `ActionScript` viewer — one tab per `:scope > DefaultAction, :scope > Action`, tab label from that action's `Description`/PreLink+Link+PostLink truncated to 40 chars, falling back to the action's `ID` attribute or `Action<N>`; each panel shows a fake "titlebar" with ID + MIMEType and a read-only `<textarea>` of the script text); `renderProperties` for Analysis (`:scope > Property` list, name from the `Name` attribute); `renderBaselineComponents` for Baseline (`:scope > BaselineComponent` list, using each component's `<Name>`/`<Relevance>`).
- A collapsed "View raw XML" `<details>` block at the end (`renderRawXmlDetails`), containing the full serialized document.

### Signature rendering (`renderSignatureDocument`)

Triggered when the parsed document's root element is `SoftwareIdentityCatalog` (matching `scripts/signature-schema.md`'s example). Unlike Task/Fixlet/Analysis/Baseline, a Signature's structured metadata comes *entirely* from its frontmatter comment — the XML body itself carries no `<Title>`/`<Description>` elements, only one or more `<Software>` detection trees. `renderSignatureDocument`:
- Extracts the frontmatter comment (`extractAttribution`) and parses it into fields (`parseFrontmatterFields`).
- Title: `fields.ProductName`, else the first `<Software>` element's `name` attribute, else the filename.
- Badge: just `"Signature"`.
- Meta line: `Publisher`, `Release`, `Author`, `uploadedOn` (labeled "Uploaded"), `Keywords` — each only if present — plus the same `metaLineFooter` (View on GitHub + Download).
- Attribution section (same as Task/Fixlet — the raw comment text in a read-only textarea).
- Description: if `fields.Description` is present, rendered as **plain text** (`textContent`, not the HTML sanitizer used for `.bes` `<Description>` — Signature descriptions come from a frontmatter comment field, not an HTML-bearing XML element, so there's nothing to sanitize as HTML).
- Detection Logic (`renderSoftwareList`): one card per `:scope > Software` element, showing its `name`/`vendor`/`version` attributes, then each of its `:scope > Signature` children as a `signature-block` (labeled `Signature <n> · modified <date>` when there's more than one), recursively rendering that Signature's filter tree via `renderSignatureFilterNode`:
  - `AND`/`OR` elements become nested, labeled, indented group boxes (`sig-group-and`/`sig-group-or`, colored differently in CSS).
  - `ExtendedSignature` is rendered as a collapsed, syntax-highlighted (`xml` language) code block via the same `makeEmbeddedCodeBlock` helper used for sanitized `<SCRIPT>`/`<STYLE>` — its content is BigFix's own mini relevance-like detection language, shown as-is rather than parsed further.
  - Any other element (e.g. `PackageFilter`, `File`) is a leaf: its tag name plus every attribute with a non-empty value, each shown as `name="value"` (via `JSON.stringify(attr.value)` for quoting).
- Finishes with the same "View raw XML" `<details>` block as other doc types.

### Attribution / frontmatter (shared)

`extractAttribution(doc)` scans the document's direct child nodes for the first XML comment whose text matches `FRONTMATTER_HINT_RE = /(^|\n)\s*(Description|Author)\s*:/i` (a heuristic to distinguish the real frontmatter block from any other leading XML comment) and returns its raw text verbatim (comment delimiters stripped, nothing else altered). This same raw text is shown as an "Attribution" section (read-only `<textarea>`, auto-sized 3–12 rows) for *every* doc type that has one — Task/Fixlet/Analysis/Baseline via `renderDocument`, unknown docs via `renderUnknown`, and Signatures via `renderSignatureDocument`. `parseFrontmatterFields(text)` (used only for Signatures) re-parses that same text into a key/value dict with the same quote-stripping rule as `generate_index.py`'s Python parser, first occurrence wins.

### Description HTML sanitizer

Applies only to `.bes` `<Description>` content (Task/Fixlet/Analysis/Baseline), via `renderSanitizedHtml` → `sanitizeNode`, which builds the untrusted HTML in a detached `<template>` and mutates its `.content` fragment in place (not string-based) before appending it, so that dynamically-created toggle buttons (see below) keep their JS event listeners.

- **Comments** are removed outright.
- **`<SCRIPT>`/`<STYLE>`** are never executed or applied: each is replaced with a collapsed toggle button (`makeEmbeddedCodeBlock`) that expands into a read-only, hljs-highlighted (`javascript`/`css` respectively) code panel showing the original source.
- **`<INPUT>`** elements are checked against `SAFE_INPUT_TYPES = {text, password, checkbox, radio, number, date, datetime-local, time, email, tel, url, range, color, search, month, week}` (case-insensitive, defaulting to `"text"` if no `type` attribute) — purely local/presentational types with no navigation, file access, or implicit form action. Anything else (`file`, `image`, `submit`, `button`, `reset`, `hidden`, ...) is replaced with `describeUnsupportedElement`, an inert, hljs-highlighted (`xml`) snippet of the original tag's `outerHTML`, so the content is still visible without being live.
- **Tag allowlist** (`ALLOWED_TAGS`): `P, A, STRONG, B, EM, I, U, BR, UL, OL, LI, SPAN, H1–H6, BLOCKQUOTE, CODE, PRE, TABLE, THEAD, TBODY, TR, TD, TH, IMG, INPUT, TEXTAREA`. Anything not in this set is **unwrapped** (its children are kept, hoisted into its parent; the tag itself is dropped) rather than removed wholesale.
- **Attribute allowlist** (`TAG_ATTR_ALLOWLIST`, applied per-tag on top of the tag allowlist — every attribute not explicitly listed for that tag is stripped, which is what prevents `onclick`/`onfocus`/etc. event-handler attributes from ever surviving): `A → href`; `IMG → src, alt, width, height`; `INPUT → type, value, placeholder, checked, disabled, readonly, maxlength, min, max, step, size`; `TEXTAREA → rows, cols, placeholder, disabled, readonly, maxlength`. Tags with no entry in the map (e.g. `P`, `SPAN`, `TABLE`, ...) have **every** attribute stripped.
- **`href`/`src` scheme checks**: `A[href]` is kept only if it matches `/^(https?:|mailto:)/i` (otherwise the attribute is dropped, leaving inert link text); `IMG[src]` is kept only if it matches `/^https?:/i`. Every surviving `<A href>` additionally gets `target="_blank"` and `rel="noopener noreferrer"` forced on.
- **`<INPUT>`** additionally gets `autocomplete="off"` forced on regardless of the original markup, so a rendered field can't get silently populated from the browser's own saved autofill data.
- Sanitization recurses into every surviving element's children (`sanitizeNode(node)` called at the end of the per-node loop).

### Styling notes

Navy/blue palette (`--navy #1b2a41`, `--accent #3f6fb4`) defined as CSS custom properties on `:root`; no dark-mode media query — one fixed light theme. Sidebar tree uses colored `type-dot`s (blue for Fixlet/Task, purple Analysis, orange Baseline, teal Signature, grey Other) matching `typeDotClass` in `app.js`. Signature `AND`/`OR` groups get distinct label-pill colors (`--accent` blue for AND, `#a35fc7` purple for OR) and a left-border indent per nesting level. ActionScript panels mimic a dark "terminal" titlebar (red/yellow/green dots). A single `@media (max-width: 800px)` breakpoint stacks the sidebar above the main content and caps sidebar height to 40vh.

## Deployment

- Published via GitHub Pages from the repo root of `Jwalker107/BigFix.We` (per `README.md`, live at `https://jwalker107.github.io/BigFix.We/`). Since `Sites/` and `Signatures/` are served as-is alongside `index.html`/`docs/`, no build or copy step is needed to publish new content — merging a `.bes` or Signature `.xml` file to `main` is sufficient; `update-index.yml` regenerates `docs/index.json` afterward so it shows up in the sidebar/search.
- **Forks**: `detectRepoConfig()` in `app.js` auto-detects `owner`/`repo` from `location.hostname`/`pathname` when served as a normal `https://<owner>.github.io/<repo>/` project site, so a fork's "View on GitHub" links point back at the fork rather than upstream — no code change needed to fork this repo and have the viewer self-link correctly. `DEFAULT_BRANCH` is not auto-detected and stays `refs/heads/main` regardless.
- **Local testing**: no dedicated test script or local server tooling was found in this repo (no `package.json`, no Makefile, no documented `python -m http.server` instructions). Because the viewer fetches `Sites/`/`Signatures/`/`docs/index.json` via relative `fetch()` calls, it needs to be served over HTTP (not opened as a `file://` URL) for those fetches to succeed — any static file server run from the repo root would work, but none is checked into or documented in this repo.

## Content-ID Assignment (`.github/workflows/update-index.yml`)

- **Trigger**: `push` to `main`, scoped to paths `Sites/**` and `Signatures/**` (so a push that only touches `docs/index.json` — e.g. the workflow's own prior commit — can't retrigger it), plus manual `workflow_dispatch`.
- **Permissions**: `contents: write`, `pull-requests: read`.
- **Concurrency**: group `${{ github.workflow }}-${{ github.head_ref || github.run_id }}`, `cancel-in-progress: true`.
- **Steps**: (1) generate a GitHub App token (`actions/create-github-app-token`, using `CICD_APP_ID`/`CICD_APP_PRIVATE_KEY` secrets) so the workflow can push back to `main` (the default `GITHUB_TOKEN` cannot push to a fork's branch, and this deliberately runs post-merge on `main` rather than at PR time); (2) checkout `main` with that token; (3) set up Python; (4) look up whether the commit's originating PR carries the `keep-content-ids` label (via `gh api repos/<repo>/commits/<sha>/pulls`, squash/rebase-merge-aware) — if so, skip ID assignment; (5) **assign content IDs**: for every `*.bes` file under any `Sites/**/Fixlets/**` path whose basename doesn't already start with `<digits>-`, rename it to `<nextid>-<basename>` (reading/incrementing `scripts/contentid.json`'s `nextid` field), sorted for deterministic ordering — a filename collision is logged as an error but does not stop the run (whatever succeeded is still committed; the job fails at the very end if any collisions occurred); (6) **regenerate `docs/index.json`** via `python scripts/generate_index.py` (run after the rename step specifically, so the index reflects the new filenames); (7) commit and push if anything changed (message includes `[skip ci]` and, when applicable, the renamed-file count), using a `github-actions[bot]` identity; (8) fail the job if any rename collisions occurred (after the safe partial commit in step 7).
- Running this on `push` to `main` (rather than at PR time) is deliberate per the workflow's own header comment: pushes to a branch are processed one at a time by GitHub, so reading-then-incrementing `scripts/contentid.json` here can't race the way two concurrent PR branches reading the same starting `nextid` could.
